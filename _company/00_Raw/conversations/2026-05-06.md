### 1. 핵심 사용자 불편함 (Pain Points) 분석

Collect가 해결하는 불편함은 단순한 '금전 부족'이 아니라, **'관계와 경험을 제대로 아카이빙하고 기념하는 데 있어 발생하는 감정적, 관계적 불편함'**입니다.

### 3. 수익화 가능성 분석 (Monetization Strategy)

수익화는 '관계 데이터의 가치'를 기반으로 한 다층적 구조(Layered Structure)를 채택해야 합니다. 단순한 거래 수수료를 넘어, 데이터의 심층성과 관계의 깊이에 따라 차등화된 프리미엄 모델을 구축해야 합니다.

#### A. 핵심 수익 모델 (Primary Revenue Stream)

1.  **거래 수수료 (Transaction Fee):**
    *   **구조:** 모금된 금액 대비 일정 비율의 수수료를 부과합니다. (기존 크라우드펀딩 모델 차용)
    *   **차별화:** 일반적인 펀딩 수수료 외에, **'관계의 깊이(Relationship Depth)'**에 따라 수수료를 차등 적용합니다. (예: 깊은 관계 기반 모금은 낮은 수수료, 단순 모금은 표준 수수료)

2.  **프리미엄 아카이빙 구독 (Premium Archiving Subscription):**
    *   **구조:** 관계 그래프 데이터의 심층 분석, 장기 추억 아카이빙, 관계 패턴 예측 등의 고급 기능에 대해 월별/연간 구독료를 부과합니다.
    *   **가치:** 사용자가 단순히 기록을 저장하는 것을 넘어, **관계 분석을 통해 통찰(Insight)**을 얻고 싶을 때 지불하게 만듭니다.

#### B. 확장 수익 모델 (Secondary Revenue Stream)

1.  **관계 데이터 API 접근 (Relationship Data API Access):**
    *   **구조:** 기업이나 연구기관이 관계 패턴 분석(예: 특정 세대의 기념일 트렌드, 커뮤니티 심리 분석)에 활용하고자 할 때, 익명화된 집단 데이터 접근 권한을 제공하고 API 사용료를 청구합니다. (가장 높은 마진 잠재력)

2.  **브랜드 제휴 및 맞춤형 경험 (Partnerships & Custom Experiences):**
    *   **구조:** 특정 관계 기반 이벤트(예: 기념일)를 기획하는 사용자에게, 관련 서비스(선물, 여행, 경험 상품)를 제공하는 제휴 파트너와 연계하여 수수료를 받습니다.

### 2. 사용자 스토리 (User Stories)

#### A. 콜렉션 생성 및 관리 (F1, F4)

*   **As a** 관계 중심의 추억을 기록하고 싶은 사용자,
    **I want to** 특정 관계(예: 친구 그룹)를 기준으로 기념일이나 특별한 경험을 묶어 '콜렉션'을 만들고 싶다,

*   **As a** 콜렉션 생성자,
    **I want to** 콜렉션에 참여한 관계들의 시간적 흐름과 상호작용을 한눈에 볼 수 있는 시각적 대시보드를 보고 싶다,
    **So that** 관계의 역동적인 변화와 연결성을 직관적으로 이해하고 공유할 수 있다.

#### B. 기억 아카이빙 및 공유 (F2, F3)

*   **As a** 추억을 공유하고 싶은 사용자,
    **I want to** 콜렉션 내에 관계와 관련된 사진, 메모, 영상을 쉽게 업로드하고 기록하고 싶다,
    **So that** 내가 경험한 감정적 맥락을 구체적인 데이터로 보존하고 공유할 수 있다.
*   **As a** 콜렉션 참여자,
    **I want to** 내가 속한 관계에게 특정 기억을 공유하고 참여를 요청할 수 있는 기능을 사용하고 싶다,
    **So that** 관계를 통해 긍정적인 경험을 확장하고 커뮤니티를 활성화할 수 있다.

#### C. 관계 및 가치 부여 (F5)

*   **As a** 관계를 소중히 여기는 사용자,
    **I want to** 관계의 깊이와 참여도에 따라 상호 존중을 표현할 수 있는 비금전적 '관계 레벨'을 부여하고 싶다,

## Collect MVP 초기 수익화 구조 기능 명세 초안

본 문서는 MVP 기능(F1~F5)을 기반으로, 관계 중심의 가치(Relationship Value)를 금전적 인센티브(Monetary Incentive)로 전환하는 초기 수익화 구조(Transaction Fee 및 레벨 시스템)의 구체적인 기능 명세 초안입니다.

### 1. 수익화 목표 및 기본 원칙

**목표:** 단순한 금전 거래가 아닌, 관계의 질과 참여에 대한 '인정'을 중심으로 수익 모델을 설계하여 사용자의 심리적 만족도를 극대화한다.

**기본 원칙:**
1.  **관계 중심 보상 (Relationship-Centric Reward):** 수익은 단순한 거래 수수료가 아닌, 관계의 깊이와 참여에 대한 인정(Recognition)으로 귀결되어야 한다.
2.  **점진적 참여 유도 (Progressive Engagement):** 낮은 참여부터 시작하여 관계의 심화에 따라 점진적으로 높은 가치(레벨, 혜택)를 제공한다.
3.  **비금전적 가치 선행 (Non-Monetary Value First):** 금전적 보상은 관계의 경험을 보존하고 심화하는 수단으로만 사용되어야 하며, 핵심 가치는 관계의 추억 아카이빙에 집중한다.

---

### 2. 핵심 수익화 메커니즘 상세 설계

#### 2.1. 트랜잭션 수수료 구조 (Transaction Fee Structure)

모든 핵심 활동에 대해 차등적인 수수료를 부과하여, 사용자가 관계를 구축하고 추억을 공유하는 행위에 대한 가치를 부여한다.

| 활동 (기능 모듈) | 수수료 유형 | 수수료율 (제안) | 비고 및 목적 |
| :--- | :--- | :--- | :--- |
| **콜렉션 생성 (F1)** | 초기 생성 수수료 | 0% (무료) | 플랫폼 참여 유도 및 관계 구축의 허들 제거 |
| **기억/경험 아카이빙 (F2)** | 기록/업로드 수수료 | 기본 0.5% | 데이터 보존에 대한 최소한의 보상 |
| **관계 초대 및 공유 (F3)** | 공유 활성화 수수료 | 1.0% | 관계의 확장에 대한 동기 부여 |
| **관계 시각화 접근 (F4)** | 대시보드 조회 수수료 | 0% (무료) | 관계의 흐름 분석은 핵심 기능으로 무료 제공 |
| **레벨 획득 (F5)** | 레벨 업그레이드 수수료 | 0% (자동 부여) | 관계의 질적 성장에 대한 보상 |

**수익화 전략:** 초기에는 핵심 기능(F1, F2)을 무료로 제공하여 사용자 유입을 극대화하고, 관계 확장에 대한 행위(F3)에 소액의 수수료를 부과하여 수익을 창출한다.

#### 2.2. 관계 레벨 및 인센티브 시스템 (Level & Incentive System)

사용자가 관계 내에서 기여하고 참여하는 정도를 측정하여, 관계의 질적 가치를 금전적/사회적 인정으로 전환한다.

**A. 레벨 체계 (Relationship Tiers):**
관계의 깊이와 참여 빈도에 따라 3단계의 레벨 시스템을 도입한다.

| 레벨 명칭 | 요구 조건 (예시) | 주요 혜택 (인센티브) | 심리적 효과 |
| :--- | :--- | :--- | :--- |
| **Seed (씨앗)** | 콜렉션 1개 생성, 5회 이상 기록 | 기본 아카이빙 공간 무제한 | 시작 단계, 추억 보존의 시작 |
| **Bloom (개화)** | 3개 이상의 활성 콜렉션 참여, 10회 이상 공유 | 특별 아카이브 테마 잠금 해제, 프리미엄 템플릿 제공 | 관계의 심화, 특별함에 대한 인정 |
| **Root (뿌리)** | 커뮤니티 내 활발한 참여, 관계 그래프 기여 | 최고 등급 배지, 관계 그룹 초대 권한 강화 | 관계의 중심, 깊은 연결에 대한 최고 인정 |

**B. 콜렉 포인트 시스템 (Collect Points):**
모든 활동(기록, 공유, 레벨 획득)에 대해 **'콜렉 포인트(CP)'**를 자동 지급한다.

*   **획득 기준:** 각 활동에 따라 차등 지급 (예: F2 기록 1회당 10 CP, F3 공유 1회당 20 CP).
*   **사용처:** 획득한 CP는 **'관계 레벨 업그레이드'** 또는 **'프리미엄 테마/템플릿 잠금 해제'**에만 사용 가능하도록 제한하여, 포인트가 단순한 화폐가 아닌 '관계의 지표'로 인식되도록 한다.

### 1. 데이터베이스 스키마 설계 (PostgreSQL 기반)

관계 그래프를 효율적으로 처리하고 관계 기반의 수익화 로직을 지원하기 위해 다음의 핵심 테이블을 설계합니다.

#### 1.1. `users` (사용자 정보)
사용자 및 관계의 주체 정보를 관리합니다.

| 필드명 | 데이터 타입 | 제약 조건 | 설명 |
| :--- | :--- | :--- | :--- |
| `user_id` | UUID | PRIMARY KEY | 사용자 고유 ID |
| `username` | VARCHAR(100) | UNIQUE, NOT NULL | 사용자 이름 |
| `created_at` | TIMESTAMP | NOT NULL | 가입일 |
| `wallet_balance` | NUMERIC(10, 2) | DEFAULT 0.00 | 현재 보유 자산 (수익화 관련) |

#### 1.2. `relationships` (관계 데이터 - 그래프의 엣지)
사용자 간의 관계 자체를 정의합니다. 이는 그래프의 엣지(Edge) 역할을 합니다.

| 필드명 | 데이터 타입 | 제약 조건 | 설명 |
| :--- | :--- | :--- | :--- |
| `relationship_id` | UUID | PRIMARY KEY | 관계 고유 ID |
| `user_a_id` | UUID | FOREIGN KEY (`users.user_id`) | 관계의 시작 사용자 ID |
| `user_b_id` | UUID | FOREIGN KEY (`users.user_id`) | 관계의 끝 사용자 ID |
| `type` | VARCHAR(50) | NOT NULL | 관계의 유형 (예: '기념일', '친구', '가족') |
| `context_data` | JSONB | | 관계에 대한 상세 맥락 정보 (기억, 이벤트 등) |
| `created_at` | TIMESTAMP | NOT NULL | 관계 생성 시점 |

#### 1.3. `collections` (콜렉션/이벤트 데이터 - 노드 및 속성)
사용자가 생성하거나 참여하는 특정 경험/이벤트(콜렉션)를 정의합니다. 이는 그래프의 노드(Node) 역할을 합니다.

| 필드명 | 데이터 타입 | 제약 조건 | 설명 |
| :--- | :--- | :--- | :--- |
| `collection_id` | UUID | PRIMARY KEY | 콜렉션 고유 ID |
| `creator_id` | UUID | FOREIGN KEY (`users.user_id`) | 콜렉션 생성자 |
| `title` | VARCHAR(255) | NOT NULL | 콜렉션 제목 |
| `event_date` | DATE | NOT NULL | 이벤트 발생 날짜 |
| `value_metric` | NUMERIC(10, 2) | | 모금된 금액 또는 관계 가치 지표 |
| `status` | VARCHAR(50) | NOT NULL | 콜렉션 상태 (예: '초기', '완료', '활성화') |

#### 1.4. `metrics` (관계 분석 및 점수 데이터)
관계 그래프 분석 API의 핵심 결과물 및 수익화 로직에 필요한 점수 데이터를 저장합니다.

| 필드명 | 데이터 타입 | 제약 조건 | 설명 |
| :--- | :--- | :--- | :--- |
| `metric_id` | UUID | PRIMARY KEY | 측정 결과 고유 ID |
| `relationship_id` | UUID | FOREIGN KEY (`relationships.relationship_id`) | 측정 대상 관계 |

### 1. 잠재 시장 규모 및 트렌드

**A. 시장 규모 추정 (Crowdfunding 및 선물 문화)**
*   **글로벌 크라우드펀딩 시장:** 지속적으로 성장하고 있으며, 특히 경험 기반(Experience-based) 펀딩 및 선물(Gifting) 관련 부문에서 높은 잠재력을 보입니다.
*   **관계 중심 경제(Relationship Economy):** 단순한 금전 거래를 넘어, 인간관계와 경험의 가치를 공유하고 추억을 아카이빙하려는 수요가 증가하고 있습니다. 이는 '기념일'이라는 특정 이벤트에 대한 감성적 가치를 상품화하려는 움직임과 일치합니다.

**B. 핵심 사용자 불편함 (Pain Points)**
사용자들이 현재 기념일 관련 활동에서 겪는 주요 불편함은 다음과 같습니다.

1.  **관계의 비가시성 (Lack of Visibility):** 관계를 기념하고 축하하는 과정이 단순한 금전적 거래에 국한되어 있어, 관계의 깊이나 감정적 맥락이 충분히 공유되고 아카이빙되지 못함.
2.  **복잡한 관리 (Management Complexity):** 여러 사람에게 개별적으로 돈을 모으고, 그 과정과 결과물을 추적하고 관리하는 과정이 분산되어 있어 번거로움.
3.  **감정적 연결 부족 (Lack of Emotional Connection):** 모금 활동이 '금전적 의무'에 초점이 맞춰져 있어, 기념일이 주는 '관계의 질적 경험'을 공유하고 축하하는 데 초점이 맞춰지지 못함.
4.  **아카이빙의 어려움 (Difficulty in Archiving):** 축하의 과정과 결과물(추억)을 체계적으로 기록하고 보존할 수 있는 통합된 공간이 부재함.

수익화는 **관계의 질적 가치(F4 분석 결과)**에 따라 차등화된 수수료 구조를 적용하여, 사용자가 돈보다 관계에 집중하도록 유도합니다.

## 관계 그래프 분석 API (`GET /api/v1/relationships/{relationship_id}/graph`) 정의 및 쿼리 로직 초안

요청하신 대로 Researcher의 관계 그래프 분석 요구사항(F1~F5 심리 점수 및 관계 연결성)과 Business의 수익화 모델을 통합하여, 특정 관계의 그래프 구조 및 심리적 가치를 계산하는 API 엔드포인트에 대한 알고리즘, 데이터 흐름, 그리고 최종 데이터베이스 쿼리 로직 초안을 정의합니다.

### 1. 알고리즘 및 데이터 흐름 (Flow) 정의

**목표:** 주어진 `relationship_id`에 대해 관계의 연결성(Graph Structure)과 심리적 가치(F1~F5 Score)를 통합하여 분석 결과를 제공한다.

**입력:** `relationship_id` (Primary Key)
**출력:** 관계 그래프 분석 결과 (JSON 형식)

**데이터 흐름 (Flow):**

1.  **관계 엔티티 조회 (Fetch Relationship Entity):**
    *   `relationship_id`를 사용하여 `Relationships` 테이블에서 해당 관계의 기본 정보(참여자, 시간 등)를 조회한다.
2.  **연결 관계 및 심리 점수 조회 (Fetch Connections & Scores):**
    *   해당 관계에 연결된 모든 관련 관계(1-hop 또는 N-hop) 및 관계 참여자들의 심리적 가치 점수(F1~F5)를 조회한다.
3.  **그래프 구조 구축 (Graph Construction):**
    *   조회된 데이터를 기반으로 `relationship_id`를 중심으로 관계의 연결 구조(예: 중심성, 연결 밀도)를 계산한다.
4.  **수익화 가치 통합 (Monetization Integration):**
    *   관계의 심리적 가치 점수(F1~F5)와 관계의 연결성(Graph Metrics)을 조합하여 잠재적인 수익화 가치 지표(예: 관계의 '잠재적 가치 점수')를 산출한다.
5.  **결과 반환 (Return Result):**
    *   계산된 그래프 구조, 심리 점수, 수익화 지표를 포함하는 최종 분석 결과를 API 응답으로 반환한다.

### 2. 최종 데이터베이스 쿼리 로직 초안 (PostgreSQL 기반)

이 로직은 관계의 **중심성(Centrality)**과 **심리적 가치(F1~F5)**를 결합하는 데 중점을 둡니다. 관계 그래프 분석을 위해 `Relationships`, `Users`, `Relationship_Scores` 테이블이 존재한다고 가정합니다.

**엔드포인트:** `GET /api/v1/relationships/{relationship_id}/graph`

**핵심 쿼리 로직 (SQL Draft):**

```sql
WITH TargetRelationship AS (
    -- 1. 목표 관계의 기본 정보 조회
    SELECT
        r.relationship_id,
        r.user_a_id AS source_user_id,
        r.user_b_id AS target_user_id,
        r.created_at
    FROM
        Relationships r
    WHERE
        r.relationship_id = :relationship_id
),
RelatedNodes AS (
    -- 2. 목표 관계와 직접 연결된 모든 노드(참여자) 및 관련 관계 조회
    SELECT
        u.user_id,
        u.name AS user_name,
        r_related.relationship_id AS related_id,
        r_related.score_f1,
        r_related.score_f2,
        r_related.score_f3,
        r_related.score_f4,
        r_related.score_f5,
        r_related.relationship_type
    FROM
        Relationships r_related
    JOIN
        Users u ON r_related.user_a_id = u.user_id OR r_related.user_b_id = u.user_id
    WHERE
        r_related.relationship_id IN (
            -- 목표 관계에 직접 연결된 관계들 (1-hop)
            SELECT relationship_id FROM Relationships WHERE user_a_id = (SELECT user_a_id FROM TargetRelationship) OR user_b_id = (SELECT user_b_id FROM TargetRelationship)
        )
)
-- 3. 최종 그래프 데이터 집계 및 분석
SELECT
    'relationship_id' AS metric_type,
    tr.relationship_id,
    -- 관계의 중심성 측정 (예: 연결된 관계의 수)
    COUNT(rn.relationship_id) AS connected_relationship_count,
    -- 심리적 가치 평균 계산 (관계의 평균 F-Score)
    AVG(rn.score_f1) AS avg_f1_score,
    AVG(rn.score_f5) AS avg_f5_score,
    -- 수익화 잠재력 지표 (F1과 F5의 차이를 기반으로 잠재적 가치 점수 산출)
    (AVG(rn.score_f5) - AVG(rn.score_f1)) * 100 AS potential_value_delta
FROM
    TargetRelationship tr
JOIN
    RelatedNodes rn ON TRUE
GROUP BY
    tr.relationship_id
ORDER BY
    potential_value_delta DESC;
```

### 3. 구현 참고 사항 (Developer Notes)

1.  **관계 그래프 데이터 모델링:** 실제 그래프 분석(N-hop 연결)을 위해서는 이 쿼리 외에 별도의 그래프 데이터베이스(예: Neo4j) 또는 PostgreSQL의 `WITH RECURSIVE` 구문을 사용하여 관계의 깊이(Depth)를 탐색하는 별도의 재귀 쿼리가 필요할 수 있습니다. 현재 쿼리는 **1-hop 연결**을 중심으로 심리 점수를 집계하는 초기 단계입니다.
2.  **수익화 모델 연동:** `potential_value_delta` 필드는 Business 모델(F1/F5 기반의 가치 측정)을 직접적으로 반영하여, 단순히 관계의 양이 아닌 **관계의 질적 감정적 맥락**을 수치화하는 데 사용됩니다.
3.  **성능 최적화:** `RelatedNodes` CTE에서 `IN` 절 대신 `LEFT JOIN`과 `EXISTS` 구문을 사용하여 데이터베이스 부하를 줄이고 쿼리 속도를 최적화해야 합니다.

## 관계 심리 점수(F1~F5) 기반 그래프 분석 상세 요구사항

Developer가 정의한 관계 그래프 분석 API(`GET /api/v1/relationships/{relationship_id}/graph`)에 관계 심리 점수(F1~F5)를 통합하여 분석 결과를 심리학적/데이터 기반으로 해석할 수 있도록 다음과 같은 상세 요구사항을 추가 제시합니다.

### 1. 핵심 분석 목표 재정의 (Goal Redefinition)

기존의 그래프 분석(중심성, 연결 밀도)에 **심리적 가치(F1~F5)**를 통합하여, 단순히 '누가 연결되어 있는가'를 넘어 '이 관계가 사용자에게 어떤 의미인가'를 측정하는 것을 목표로 합니다.

**새로운 목표:** 관계의 **구조적 중요성(Structural Importance)**과 **감정적 깊이(Emotional Depth)** 간의 상관관계를 분석하여, 관계의 잠재적 가치(Potential Value)를 정량화합니다.

### 2. F1~F5 점수의 그래프 지표 반영 방법

각 F1~F5 점수는 그래프 분석 결과에 다음과 같이 가중치 또는 필터로 적용되어야 합니다.

#### A. 중심성(Centrality)의 심리적 재해석

기존의 그래프 중심성 지표(Degree Centrality, Betweenness Centrality 등)를 심리적 가치에 따라 가중치를 부여하여 재해석합니다.

1.  **감정적 중심성 (Emotional Centrality):**
    *   **정의:** 관계의 연결성(Degree)이 높은 것뿐만 아니라, 그 관계가 참여하는 모든 관계의 평균 심리 점수($\text{Avg}(F1\sim F5)$)를 반영하여 계산합니다.
    *   **목표:** 단순히 많은 관계를 맺고 있는 사람보다, **깊고 의미 있는 관계**를 맺고 있는 사람을 더 중요한 중심 노드로 식별합니다.
    *   **계산 예시:** $\text{Emotional Centrality} = \text{Degree Centrality} \times \text{Weighted Average of Neighbors' Scores}$

2.  **영향력 중심성 (Influence Centrality):**
    *   **정의:** 관계의 연결 경로(Betweenness)가 얼마나 많은 관계의 흐름을 통제하는지를 측정합니다.
    *   **목표:** 관계의 **중개자 역할**과 **관계의 흐름**을 통해 심리적 가치를 전달하는 핵심 인물을 식별합니다.

#### B. 연결 밀도(Density)의 감정적 필터링

관계 밀도(Density)는 관계의 양적 측면을 나타내지만, 감정적 깊이를 반영하기 위해 필터링이 필요합니다.

1.  **심리적 밀도 (Psychological Density):**
    *   **정의:** 관계 밀도 내에서, 해당 관계들의 평균 심리 점수가 특정 임계치(예: 평균 F-Score > 3.0) 이상인 관계의 비율을 측정합니다.
    *   **목표:** 관계가 **얕은 교류**가 아닌, **깊은 감정적 연결**로 이루어져 있는지를 판단합니다. 낮은 심리 점수를 가진 관계는 밀도 계산에서 가중치를 낮춥니다.

#### C. 잠재적 가치 지표 산출 (Derived Metric)

최종적으로 API 응답에는 다음의 핵심 지표를 포함해야 합니다.

1.  **관계의 총 심리 가치 점수 (Total Psychological Value Score):**
    *   해당 관계의 모든 참여자들의 F1~F5 점수를 종합하여 산출한 가중 평균 점수 (예: $\text{Average}(F1\sim F5)$).
2.  **관계의 깊이 지수 (Depth Index):**
    *   관계의 연결성(Path Length)과 평균 심리 점수의 조합을 통해, 관계가 얼마나 복잡하고 깊은 맥락을 가지고 있는지를 나타내는 지표. (예: 짧은 경로 + 높은 평균 점수 = 높은 깊이)
3.  **수익화 잠재력 점수 (Monetization Potential Score):**
    *   관계의 심리적 가치 점수와 잠재적 수익화 모델(Transaction Fee 구조)을 결합하여, 이 관계가 플랫폼에서 수익화될 잠재력이 얼마나 높은지를 예측하는 지표. (이는 Business 에이전트의 수익화 모델과 직접 연동됨)

## 관계 그래프 분석 API 구현 초안 (GET /api/v1/relationships/{relationship_id}/graph)

CEO 지시에 따라, 관계 심리 점수(F1~F5)가 통합된 관계 그래프 분석 API의 최종 알고리즘 및 RESTful API 엔드포인트 구현 초안을 제시합니다. 이 구현은 PostgreSQL 기반의 관계 그래프 데이터 모델을 기반으로 합니다.

### 1. API 엔드포인트 정의

**Endpoint:** `GET /api/v1/relationships/{relationship_id}/graph`

**목적:** 특정 관계 ID에 대한 심리적 가치와 연결성을 종합적으로 분석하여 반환합니다.

**Request Parameters:**
*   `relationship_id`: 분석하고자 하는 관계의 고유 ID (Primary Key)

**Response Structure (JSON 예시):**
```json
{
  "relationship_id": "REL_12345",
  "relationship_summary": "관계 분석 결과 요약",
  "emotional_score": {
    "F1_Intimacy": 4.5,  // 친밀도 점수 (F1~F5)
    "F2_Trust": 4.0,     // 신뢰 점수
    "F3_Shared_Experience": 3.5, // 공유 경험 점수
    "F4_Reciprocity": 4.8,  // 상호성 점수
    "F5_Value_Recognition": 4.2 // 가치 인정 점수
  },
  "graph_metrics": {
    "connection_density": 0.75, // 관계 연결 밀도 (0.0 ~ 1.0)
    "emotional_flow_score": 4.1 // 감정 흐름 점수 (F1~F5 가중치 적용)
  },
  "temporal_flow": {
    "time_since_last_interaction_days": 15, // 마지막 상호작용 후 경과 일수
    "relationship_history_trend": "Stable_Positive" // 관계 변화 추이
  }
}
```

### 2. 데이터베이스 쿼리 로직 및 알고리즘 초안 (PostgreSQL 기반)

이 API는 관계 테이블(`relationships`), 사용자 테이블(`users`), 그리고 관계 심리 점수 테이블(`emotional_scores`)을 조인하여 최종 그래프 지표를 계산해야 합니다.

**핵심 알고리즘:**
1.  **관계 심리 점수 통합:** 관계에 연결된 모든 참여자의 F1~F5 점수를 평균 또는 가중 평균하여 관계의 전반적인 감정적 맥락 점수를 산출합니다.
2.  **관계 연결성 계산 (Graph Metric):** 관계 내의 연결 빈도와 깊이를 측정하여 연결 밀도(Connection Density)를 계산합니다.
3.  **시간적 흐름 분석:** 관계 기록 테이블을 참조하여 마지막 상호작용 시점과 현재 시점의 차이를 계산하여 관계의 동적인 흐름을 파악합니다.

**PostgreSQL 쿼리 로직 초안 (Pseudo-SQL):**

```sql
WITH RelationshipDetails AS (
    -- 1. 관계의 핵심 심리 점수 및 참여자 정보 추출
    SELECT
        r.relationship_id,
        u1.f1 AS intimacy_score,
        u2.f1 AS trust_score,
        u1.f5 AS value_recognition_score,
        r.start_date,
        r.last_interaction_date
    FROM
        relationships r
    JOIN
        users u1 ON r.user_id_1 = u1.user_id
    JOIN
        users u2 ON r.user_id_2 = u2.user_id
    WHERE
        r.relationship_id = :relationship_id
),
GraphMetrics AS (
    -- 2. 관계 연결 밀도 계산 (관계 그래프의 연결성)
    SELECT
        COUNT(DISTINCT user_id) AS total_participants,
        -- 연결 밀도 예시: 관계 내 참여자 수 대비 관계의 깊이 (복잡한 그래프 알고리즘 필요)
        -- 단순화를 위해, 관계 내 모든 상호작용의 밀도를 측정한다고 가정
        COALESCE(SUM(CASE WHEN r.interaction_count > 0 THEN 1 ELSE 0 END), 0) AS interaction_count
    FROM
        relationships r
    WHERE
        r.relationship_id = :relationship_id
)
-- 3. 최종 결과 집계
SELECT
    rd.relationship_id,
    -- 감정 점수 통합 (가중치 적용 예시: F5(가치 인정)에 더 높은 가중치 부여)
    (rd.intimacy_score * 0.2 + rd.trust_score * 0.2 + rd.value_recognition_score * 0.4 + (SELECT f5 FROM emotional_scores WHERE relationship_id = rd.relationship_id) * 0.4) AS emotional_flow_score,
    
    -- 그래프 지표
    (SELECT COUNT(*) FROM RelationshipDetails) AS total_participants,
    (SELECT interaction_count FROM GraphMetrics) AS connection_density,
    
    -- 시간적 흐름
    EXTRACT(EPOCH FROM (NOW() - rd.last_interaction_date)) / (60*60*24) AS time_since_last_interaction_days,
    
    -- 관계 요약
    CASE
        WHEN (rd.intimacy_score + rd.trust_score) >= 8.0 THEN 'Deeply Connected'
        WHEN (rd.intimacy_score + rd.trust_score) >= 6.0 THEN 'Strong Bond'
        ELSE 'Developing Connection'
    END AS relationship_summary
FROM
    RelationshipDetails rd
JOIN
    GraphMetrics gm ON TRUE;
```

## 관계 그래프 분석 API 구현 초안 (GET /api/v1/relationships/{relationship_id}/graph)

CEO 지시에 따라, 관계 심리 점수(F1~F5)가 통합된 관계 그래프 분석 API의 최종 알고리즘 및 RESTful API 엔드포인트 구현 초안을 제시합니다. 이 구현은 PostgreSQL 기반의 관계 그래프 데이터 모델을 기반으로 합니다.

### 1. API 엔드포인트 정의

**Endpoint:** `GET /api/v1/relationships/{relationship_id}/graph`

**목적:** 특정 관계 ID에 대한 심리적 가치와 연결성을 종합적으로 분석하여 반환합니다.

**Request Parameters:**
*   `relationship_id`: 분석하고자 하는 관계의 고유 ID (Primary Key)

**Response Structure (JSON 예시):**
```json
{
  "relationship_id": "REL_12345",
  "relationship_summary": "관계 분석 결과 요약",
  "emotional_score": {
    "F1_Intimacy": 4.5,  // 친밀도 점수 (F1~F5)
    "F2_Trust": 4.0,     // 신뢰 점수
    "F3_Shared_Experience": 3.5, // 공유 경험 점수
    "F4_Reciprocity": 4.8,  // 상호성 점수

  }
```

### 2. 데이터베이스 쿼리 로직 및 알고리즘 초안 (PostgreSQL 기반)

이 API는 관계 테이블(`relationships`), 사용자 테이블(`users`), 그리고 관계 심리 점수 테이블(`emotional_scores`)을 조인하여 최종 그래프 지표를 계산해야 합니다.

**핵심 알고리즘:**
1.  **관계 심리 점수 통합:** 관계에 연결된 모든 참여자의 F1~F5 점수를 평균 또는 가중 평균하여 관계의 전반적인 감정적 맥락 점수를 산출합니다.
2.  **관계 연결성 계산 (Graph Metric):** 관계 내의 연결 빈도와 깊이를 측정하여 연결 밀도(Connection Density)를 계산합니다.
3.  **시간적 흐름 분석:** 관계 기록 테이블을 참조하여 마지막 상호작용 시점과 현재 시점의 차이를 계산하여 관계의 동적인 흐름을 파악합니다.

**PostgreSQL 쿼리 로직 초안 (Pseudo-SQL):**

```sql
WITH RelationshipDetails AS (
    -- 1. 관계의 핵심 심리 점수 및 참여자 정보 추출
    SELECT
        r.relationship_id,
        u1.f1 AS intimacy_score,
        u2.f1 AS trust_score,
        u1.f5 AS value_recognition_score,
        r.start_date,
        r.last_interaction_date
    FROM
        relationships r
    JOIN
        users u1 ON r.user_id_1 = u1.user_id
    JOIN
        users u2 ON r.user_id_2 = u2.user_id
    WHERE
        r.relationship_id = :relationship_id
),
GraphMetrics AS (
    -- 2. 관계 연결 밀도 계산 (관계 그래프의 연결성)
    SELECT
        COUNT(DISTINCT user_id) AS total_participants,
        -- 연결 밀도 예시: 관계 내 참여자 수 대비 관계의 깊이 (복잡한 그래프 알고리즘 필요)
        -- 단순화를 위해, 관계 내 모든 상호작용의 밀도를 측정한다고 가정
        COALESCE(SUM(CASE WHEN r.interaction_count > 0 THEN 1 ELSE 0 END), 0) AS interaction_count
    FROM
        relationships r
    WHERE
        r.relationship_id = :relationship_id
)
-- 3. 최종 결과 집계
SELECT
    rd.relationship_id,
    -- 감정 점수 통합 (가중치 적용 예시: F5(가치 인정)에 더 높은 가중치 부여)
    (rd.intimacy_score * 0.2 + rd.trust_score * 0.2 + rd.value_recognition_score * 0.4 + (SELECT f5 FROM emotional_scores WHERE relationship_id = rd.relationship_id) * 0.4) AS emotional_flow_score,
    
    -- 그래프 지표
    (SELECT COUNT(*) FROM RelationshipDetails) AS total_participants,
    (SELECT interaction_count FROM GraphMetrics) AS connection_density,
    
    -- 시간적 흐름
    EXTRACT(EPOCH FROM (NOW() - rd.last_interaction_date)) / (60*60*24) AS time_since_last_interaction_days,
    
    -- 관계 요약
    CASE
        WHEN (rd.intimacy_score + rd.trust_score) >= 8.0 THEN 'Deeply Connected'
        WHEN (rd.intimacy_score + rd.trust_score) >= 6.0 THEN 'Strong Bond'
        ELSE 'Developing Connection'
    END AS relationship_summary
FROM
    RelationshipDetails rd
JOIN
    GraphMetrics gm ON TRUE;
```

## 관계 그래프 분석 API 최종 요구사항 및 UX 영향 분석

CEO님의 지시에 따라 관계 그래프 분석 API에 포함되어야 할 핵심 기능(F1~F5 심리 점수 및 관계 연결성)에 대한 최종 요구사항을 정리하고, 이것이 사용자 경험(UX)에 미치는 영향을 분석하여 개발 우선순위를 제시합니다.

### 1. 핵심 기능 요구사항 정의

관계 그래프 분석 API(`GET /api/v1/relationships/{relationship_id}/graph`)는 단순한 연결 정보 제공을 넘어, 관계의 **감정적 맥락**과 **잠재적 가치**를 정량화하여 사용자에게 제공해야 합니다.

#### 1.1. 관계 심리 점수 (F1~F5) 요구사항
이 점수는 관계의 질적 깊이를 측정하며, 데이터 모델링의 핵심이 됩니다.

| 지표 | 정의 (심리학적 맥락) | 데이터 모델링 요구사항 | API 반영 방식 |
| :--- | :--- | :--- | :--- |
| **F1 (신뢰/Trust)** | 관계의 안정성과 상호 믿음의 정도 | 1~5점 척도 (1: 불신, 5: 절대적 신뢰) | 관계 그래프의 노드(Node) 가중치로 반영 |
| **F2 (친밀도/Intimacy)** | 관계의 감정적 공유 및 깊이의 정도 | 1~5점 척도 (1: 얕음, 5: 깊은 유대감) | 관계 간의 연결 강도(Edge Weight) 산출에 사용 |
| **F3 (공유 활성화/Sharing)** | 관계 내에서 정보나 경험을 공유하는 빈도 및 의지 | 0~100% 또는 1~5점 척도 | 관계 그래프 내의 상호작용 흐름(Flow) 지표로 반영 |
| **F4 (상호 지원/Support)** | 어려움에 처했을 때 서로를 지지하는 정도 | 1~5점 척도 (1: 지지 없음, 5: 적극적 지원) | 관계 그래프의 연결 밀도(Density) 및 균형 지표로 반영 |
| **F5 (유대감/Bond)** | 관계의 지속성과 감정적 결속의 깊이 | 1~5점 척도 (1: 약함, 5: 강한 유대) | 관계 그래프의 중심성(Centrality) 지표 가중치로 반영 |

**최종 요구사항:** 모든 F1~F5 점수는 단순한 수치가 아닌, **관계 그래프의 노드 및 엣지(연결)의 가중치**로 변환되어야 합니다.

#### 1.2. 관계 연결성 요구사항
단순 연결을 넘어, 관계의 역동성과 흐름을 분석하는 지표를 포함해야 합니다.

*   **연결 밀도 (Density):** 특정 관계 내에서 발생하는 상호작용의 빈도와 깊이를 측정하여, 관계의 '밀도'를 수치화합니다.
*   **감정 흐름 점수 (Emotional Flow Score):** F1~F5 점수들의 시간적 흐름(Timeline)을 분석하여, 관계가 긍정적/부정적 방향으로 어떻게 발전해왔는지(추억 아카이빙의 흐름)를 시각화합니다.
*   **관계 중심성 (Centrality):** 해당 관계가 사용자의 전체 관계 네트워크 내에서 얼마나 중요한 위치(핵심 축)를 차지하는지를 측정합니다.

### 2. 수익화 로직 초기 명세 (Monetization Logic Specification)

관계의 심리적 가치와 그래프 지표를 기반으로 Transaction Fee 및 Level System을 설계합니다.

#### 2.1. Transaction Fee (거래 수수료) 로직
**목표:** 관계 데이터에 접근하거나 분석할 때, 관계의 질적 깊이(F1~F5)에 비례하여 수수료를 차등 부과합니다.

**기본 공식:**
$$\text{Fee} = \text{Base Rate} \times \text{Relationship Multiplier}$$

**관계 멀티플라이어 ($\text{Relationship Multiplier}$) 정의:**
이 지표는 관계의 질적 깊이($\text{F1}$과 $\text{F5}$)와 관계의 역동성($\text{Connection Density}$)을 결합하여 산출합니다.

$$\text{Multiplier} = \text{Base Value} \times (\text{F1} + \text{F5}) \times (1 + \text{Connection Density} \times \text{Weight}_{\text{Flow}})$$

*   **$\text{Base Value}$:** 기본 거래 금액 (예: $10).
*   **$\text{Weight}_{\text{Flow}}$:** 감정 흐름 점수($\text{Emotional Flow Score}$)의 가중치. 관계의 발전 과정이 명확할수록(흐름이 좋을수록) 수수료가 증가합니다.
*   **실행 로직:**
    1.  사용자가 특정 관계의 그래프 분석(예: 관계 중심성 확인)을 요청할 때, 시스템은 해당 엣지의 $\text{F1}, \text{F5}, \text{Connection Density}$를 조회합니다.
    2.  위 공식을 사용하여 $\text{Multiplier}$를 계산합니다.
    3.  $\text{Fee}$를 계산하고, 이 금액을 $\text{Transaction Value}$에 추가하여 최종 수수료를 산출합니다.

**목표:** 사용자가 관계를 깊이 있게 아카이빙하고, 플랫폼에 기여할수록 더 높은 등급을 부여하여 지속적인 참여를 유도합니다.

### 📍 1. 시장의 문제점: '공허한 기념일'의 한계 (The Problem)

*   **관계의 정량화:** 복잡한 관계의 역학을 '관계 그래프'라는 데이터 모델로 시각화하여, 관계의 온기를 눈에 보이는 형태로 제시합니다.

### 🚀 3. 사용자 경험의 변화: '관계 데이터'를 통한 재발견 (The Outcome)
Collect는 사용자에게 단순히 돈을 모으게 하는 것이 아니라, **자신과 타인의 관계를 객관적이고 아름답게 성찰할 기회**를 제공합니다.

*   **새로운 의미 부여:** 기념일이 관계의 '마일스톤'이자 '추억의 증명서'가 됩니다.

```sql
-- Table: relationships (관계 엔티티)
CREATE TABLE relationships (
    relationship_id SERIAL PRIMARY KEY,
    user_id_a INTEGER NOT NULL REFERENCES users(user_id), -- 관계의 한쪽 사용자 ID
    user_id_b INTEGER NOT NULL REFERENCES users(user_id), -- 관계의 다른 쪽 사용자 ID
    relationship_type VARCHAR(100) NOT NULL,        -- 관계의 종류 (예: 친구, 가족, 동료)
    start_date DATE NOT NULL,                        -- 관계 시작일
    end_date DATE,                                    -- 관계 종료일 (NULL이면 현재 진행 중)

    connection_density NUMERIC(5, 2) NOT NULL,       -- 관계 연결 밀도 지표 (0.00 ~ 1.00)
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE user_relationships_metrics (
    metric_id SERIAL PRIMARY KEY,
    relationship_id INTEGER UNIQUE NOT NULL REFERENCES relationships(relationship_id),
    f1_score NUMERIC(3, 2) NOT NULL, -- 관계 심리 점수 F1
    f2_score NUMERIC(3, 2) NOT NULL, -- 관계 심리 점수 F2
    f3_score NUMERIC(3, 2) NOT NULL, -- 관계 심리 점수 F3
    f4_score NUMERIC(3, 2) NOT NULL, -- 관계 심리 점수 F4
    f5_score NUMERIC(3, 2) NOT NULL, -- 관계 심리 점수 F5
    emotional_context_score NUMERIC(3, 2) NOT NULL, -- 관계 감정적 맥락 점수 (별도 계산된 점수)
    transaction_fee_applied NUMERIC(5, 2) DEFAULT 0.00, -- 적용된 거래 수수료 (수익화 모델 연동)
    level_status VARCHAR(50) DEFAULT 'Standard', -- 관계 레벨 상태 (F1~F5 기반)
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Index for faster lookups on relationships
CREATE INDEX idx_relationships_user_id_a ON relationships(user_id_a);
CREATE INDEX idx_relationships_user_id_b ON relationships(user_id_b);
```

### 2. 그래프 시각화: 관계 연결성 (Relationship Graph Visualization)

사용자가 관계들 간의 연결 밀도와 감정 흐름을 파악할 수 있도록 관계 그래프를 구성합니다.

*   **레이아웃:** 중앙 집중형 노드-링크(Node-Link) 구조를 채택합니다.
*   **노드(Node):** 각 사용자 또는 관계 집합을 나타냅니다.
    *   **스타일:** 부드러운 모서리(Rounded Corners)를 가진 원형 노드.
    *   **내부 정보:** 사용자 이름과 관계의 평균 온기 점수(F1~F5)를 노드 내부에 작게 표시합니다.
*   **링크(Link):** 노드 간의 연결을 나타냅니다.
    *   **두께:** 연결 밀도(`connection_density`)에 비례하여 선의 두께를 조정합니다.
    *   **색상:** 연결된 관계의 평균 감정 점수(F1~F5)에 따라 선의 색상을 미묘하게 변화시킵니다. (점수가 높을수록 골드/앰버 톤)

**[시각화 규칙 요약]**

1.  **관계의 깊이:** F1~F5 점수는 **색상과 게이지**를 통해 즉각적으로 전달되어야 합니다.
2.  **연결의 강도:** 연결 밀도는 **선 두께**를 통해 전달되어야 합니다.
3.  **톤앤매너:** 전체적으로 그림자(Shadow)와 부드러운 그라데이션을 사용하여 '따뜻함'과 '기억'의 감성적 깊이를 유지합니다.
